# DevCrew: สรุปผลสำหรับสัมภาษณ์ (2026-10-14)

## คำถามที่ผมตั้ง
"ระบบ AI แบบทีม (Planner → QA → Dev → Verify → Reviewer) ดีกว่า AI ตัวเดียวจริงไหม และดีกว่าในงานแบบไหน"

## วิธีวัด (จุดที่อยากให้เห็น)
- **ตัดสินผลด้วยเทสต์ที่ซ่อนไว้:** AI ไม่เห็นเทสต์ชุดนี้ เทสต์ถูกคัดลอกเข้าไปตอนตรวจเท่านั้น
- **ตรวจตัวตรวจก่อนใช้งาน:**
  - ทุกชุดมีโค้ดอ้างอิงที่ผ่านครบ
  - จงใจใส่บั๊กลงในโค้ดอ้างอิง เพื่อเช็กว่าเทสต์จับได้จริง
- **บันทึกสมมติฐานก่อนรันทุกครั้ง:** อยู่ใน `docs/STATUS.md` และรายงานผลทั้งหมด รวมถึงผลที่ไม่เข้าข้างตัวเอง
- **ไม่เลือกเฉพาะ run ที่ดี:** run ที่เสียเพราะบั๊กของเครื่องมือจะแยกเก็บพร้อมเหตุผล แล้วรันใหม่ทั้งชุด

## ข้อสรุป
1. **งานซอฟต์แวร์ที่สเปกชัดและตรวจผลในเครื่องได้:**
   - โมเดลปัจจุบันทำได้ครบด้วยตัวเดียว ซื่อตรง และวางโครงสร้างโค้ดได้ดี
   - การใช้ทีมเพิ่มต้นทุน 5–50× โดยไม่ได้คุณภาพเพิ่ม
2. **คุณค่าของทีมอยู่ที่การควบคุม:**
   - เทสต์ถูกล็อกด้วย hash จึงแก้ไม่ได้
   - Dev เขียนไฟล์นอกขอบเขตไม่ได้
   - มีคนอนุมัติที่ gate
   - Verify ที่ไม่ใช่ AI เป็นคนตัดสินว่า "เสร็จ"
   - มี audit log ครบ
   - สิ่งเหล่านี้คือสิ่งที่องค์กรต้องการเมื่อความผิดพลาดมีราคาแพง
3. **การทดสอบช่วยปรับระบบ:** benchmark หาบั๊กในระบบทีมได้จริง แต่ละตัวแก้แล้ว และมีเทสต์กันไว้
   - วนวางแผนใหม่ไม่รู้จบ
   - หมดเวลาแล้วไม่หยุด
   - เทสต์ที่ผิดทำให้ต้องทำใหม่ทั้งงาน (62–84% ของต้นทุน)
   - Verify อ่านผลเทสต์ของ PlatformIO ไม่ได้

## บทเรียนจาก hardware
- **ประกอบโมดูลช้าเกินไป:** ทีมเขียนโมดูลครบ แต่ `main.cpp` ยังว่าง เพราะหมดเวลาก่อนประกอบ บอร์ดจึงได้ 0/9
  - **แนวทางแก้:** ทำ integration ตั้งแต่โมดูลแรก และรัน HIL ทุกรอบ
- **เทสต์ที่ล็อกไว้มีบั๊ก:** Dev แก้ไม่ได้ ทั้งระบบจึงติด
  - **แนวทางแก้:** QA ต้องพิสูจน์ว่าเทสต์ build ได้ก่อนล็อก

## การตัดสินใจที่ผมแนะนำ
- **งานทั่วไป:** ใช้ AI ตัวเดียว
- **งานเสี่ยงสูง:** ใช้ส่วนที่ดีของ DevCrew คือ hash-locked tests, non-AI Verify, approval gate และ audit log
  - ไม่ต้องใช้ pipeline เต็มทุกขั้น
- **ถ้าจะลงทุนกับทีมเต็มรูปแบบ:** ใช้กับงานที่ AI ตรวจผลเองไม่ได้ เช่น งาน hardware
