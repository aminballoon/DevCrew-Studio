Hardware-in-the-loop (ESP32)

บอร์ด Waveshare ESP32-S3-ETH-8DI-8RO ต่อ USB จริง ตัวตรวจไม่ใช่ AI ระบบจะ flash firmware แล้วคุยกับบอร์ดผ่าน serial ทั้งหมด 9 ข้อ:

  • อ่านสถานะรีเลย์กลับจากชิป
  • RTC ต้องเดินต่อหลังรีเซ็ต
  • เปิดรีเลย์ได้ไม่เกิน 4 ตัว
  • watchdog ปิดรีเลย์เอง
  • บอร์ดต้องไม่ล่มเมื่อเจอข้อมูลขยะ

สเปกจงใจใส่ข้อมูลผิดไว้: address 0x27 (ของจริงคือ 0x20), ขา I2C ผิด, library ที่ไม่มีอยู่จริง และคำแนะนำให้ erase flash

ทำไมทีมได้ 0: ทีม #3 หมดเวลา 60 นาทีตอนที่ main.cpp ยังว่าง ส่วนทีม #2 ล้มเพราะบั๊กของ DevCrew เอง (git output ล้น buffer เพราะโฟลเดอร์ build ของ firmware ใหญ่มาก) บั๊กนี้แก้แล้ว แต่ยังไม่ได้รันซ้ำ ผลของทีมจึงยังสรุปไม่ได้เต็มที่

ชุดแรกถูกแยกเก็บ (hil-haiku-v1) เพราะ Verify ของทีมอ่านผลของ pio test ไม่ได้ ทำให้ทีมวนแก้งานที่ผ่านแล้วจนหมดเวลา ในชุดนั้น Single ผ่านครบ 1 ใน 3 รอบ (2/9, 8/9, 9/9) ผมแก้บั๊กแล้วรันใหม่ทั้งชุด

บทเรียนจากงาน hardware (ยังไม่ได้แก้)

  • ประกอบโมดูลช้าเกินไป: ทีม #3 เขียนโมดูลครบ 3 ตัว (protocol 199 บรรทัด, relay 79 บรรทัด, board-io 129 บรรทัด) แต่ main.cpp ยังเป็นไฟล์เปล่าจาก seed เพราะหมดเวลาก่อนถึงขั้นประกอบ บอร์ดจึงไม่ตอบอะไรเลย (0/9)
  • แนวทางแก้: เพิ่มขั้น integration ตั้งแต่โมดูลแรก ให้ firmware ทำงานบนบอร์ดได้แบบบางที่สุดก่อน แล้วค่อยเพิ่มความสามารถทีละโมดูล โดยรัน HIL ทุกรอบ แทนการประกอบตอนท้าย
  • เทสต์ที่ล็อกไว้แต่มีบั๊ก ทำให้ทั้งระบบติด: สคริปต์เทสต์ของ QA สั่ง build ทุก environment รวม native ซึ่งล้มทุกครั้ง แต่ Dev แก้ไม่ได้ เพราะเทสต์ถูกล็อกไว้กันโกง
    • แนวทางแก้: ให้ QA พิสูจน์ว่าเทสต์ build ได้และ fail อย่างถูกต้องกับโค้ดเปล่าก่อนล็อก

บั๊กที่ benchmark ช่วยหาเจอในระบบทีม (แก้แล้ว พร้อมเทสต์)

  • เทสต์ผิดหนึ่งข้อทำให้ต้องวางแผนและทำใหม่ทั้งหมด กินต้นทุน 62–84% → เพิ่มขั้น QA dispute ต้นทุนลดลงราว 40%
  • ความขัดแย้งที่ต้องให้คนตัดสินทำให้ทีมวนวางแผนใหม่ไม่รู้จบ → จำกัด 2 รอบ แล้วหยุดถามคน
  • หมดเวลาแล้ว run ไม่หยุด → ยกเลิก run จริงเมื่อหมดเวลา
  • Verify อ่านผลเทสต์ firmware (PlatformIO) ไม่ได้ → เพิ่มตัวอ่าน

ข้อสรุป

  • งานซอฟต์แวร์ที่สเปกชัดและตรวจผลในเครื่องได้: AI ตัวเดียวพอแล้ว เพราะคุณภาพเท่ากัน ซื่อตรง และวางโครงสร้างได้ดี ส่วนทีมเพิ่มต้นทุน 5–50×
  • คุณค่าของทีมคือการควบคุม: ล็อกเทสต์ด้วย hash, Dev เขียนนอกขอบเขตไม่ได้, คนอนุมัติที่ gate, Verify ที่ไม่ใช่ AI ตัดสินว่า "เสร็จ" และมี audit log ครบ
  • งาน hardware: ผลต่างจากที่คาดไว้ Haiku ตัวเดียวทดสอบบนบอร์ดเองผ่าน serial ได้ และผ่านครบ 3/3 ส่วนทีมแพ้ เพราะกระบวนการช้าเกินไป (QA ใช้เวลานาน, ประกอบโมดูลตอนท้าย, เทสต์ที่ล็อกไว้มีบั๊ก) และมีบั๊กในตัว DevCrew

คำแนะนำ

  • งานทั่วไปใช้ AI ตัวเดียว
  • งานเสี่ยงสูงใช้เฉพาะกลไกควบคุมของ DevCrew ไม่ต้องใช้ pipeline เต็ม
  • งาน hardware ต้องปรับ pipeline ก่อน คือทำ integration ตั้งแต่โมดูลแรก และให้ QA พิสูจน์ว่าเทสต์ build ได้ก่อนล็อก แล้วค่อยวัดใหม่
